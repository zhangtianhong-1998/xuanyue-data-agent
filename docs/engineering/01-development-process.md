# 研发流程与仓库约定

日期：2026-09-24；本项目当前处于 G0 需求与技术路线评审。

## 1. 用小阶段推进

| 阶段 / 评审点 | 要完成什么 | 用户要决定什么 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| G0 需求与技术路线 | 产品需求、用户故事、竞品/源码研究、关键实验、候选方案 | 首个行业场景、首版边界、候选路线 | 记录确认与仍未解决的问题；本轮停在这里讨论 |
| G1 详细设计 | 页面草图、数据契约、权限方案、错误状态、验收数据集 | 关键操作是否符合预期、授权体验 | 核心故事可测试，打包/兼容风险有实验计划 |
| G2 最小完整原型（M1） | 导入→提问→本地计算→下钻→报告 | 实际结果与交互是否值得继续 | 开发 Mac 端到端演示通过；没有把模拟模型结果当真实完成 |
| G3 个人 MVP（M2） | 扩展格式、受控多 Agent、Skill/MCP/Memory、流程恢复 | 哪些功能继续打磨、是否邀请他人试用 | 三系统 smoke、关键错误场景、回归数据集、依赖许可检查 |
| G4 版本发布与迭代 | 安装包、升级/回退、使用说明、已知问题 | 是否分发，分发给谁 | 版本标签、安装验收记录、备份与恢复方法 |

每个阶段可以返回上一步。只有会改变目标用户、权限范围、费用、数据外发或主要开发成本的取舍才需要用户参与；日常实现细节由研发自行处理。

## 3. Git 管理

- 当前目录初始化为主仓库，设计文档与自编实验代码一起追踪。尚未创建远程仓库或上传任何内容。
- 外部源码各自是独立 Git 仓库，主仓库记录 URL、固定 commit、许可证和获取方式。避免把几个大型上游整仓复制进产品历史。
- 首次研究结果形成一个可审查提交；后续按 `docs/...`、`spike/...`、`feat/...` 等短分支开发，每个改动说明对应故事与验证。
- ADR 是架构决策记录，保存背景、候选、依据、代价和复审条件。`proposed` 只有在用户评审后才能改为 `accepted`。
- 需求变更写入文档和提交，不依赖聊天记录作为唯一依据。
- 真正的密钥、业务文件、运行数据库、依赖目录和构建产物不入 Git。实验仅提交可公开的合成输入与精简结果。
- 本轮未替用户选择产品开源许可证；确定商业/分发方式后再选，外部组件许可单独核验。

## 4. 一个故事如何进入开发

1. 选一个可演示的用户行为，写清正常、错误、取消三类路径。
2. 确定输入、输出、权限、日志、数据版本及验收答案。
3. 画必要的界面草图，定义契约后实现最小链条。
4. 运行与风险匹配的验证：数值算法测固定答案；权限/恢复测失败路径；布局和交互做界面验证。
5. 用户演示验收；记录已知限制。完成后再扩展到下一故事。

“完成”至少意味着：实现可运行、验收条件有结果、失败不会伪报成功、文档和版本一致。测试数量多不等于业务效果好。

## 5. 模型和分析评测

准备三组互不混淆的验证：

- 工程：协议、事件顺序、取消、重启、权限、打包和文件读写。
- 计算：冻结文件/口径/答案，核对聚合、分母、时间、连接、贡献与下钻。
- Agent：问题澄清、选工具、证据使用、不可回答处理、解释质量、成本。需要真实模型，且保留失败和未判断任务。

先以单 Agent 做基线，再评测多 Agent 是否提高准确率或覆盖率，以及增加了多少费用和延迟。禁止只展示成功的轨迹，也不把模拟节点的恢复成功当作智能分析效果。
