## 现在做到哪里

现有实验已经证明：LangGraph 可以运行一个固定流程并在指定位置恢复；AgentScope 独立根任务可用合成模型调用本地工具并输出公开片段；LangGraph 主任务可通过 A2A 调用 AgentScope 子任务。这些是局部工程结果。**AgentScope 根任务的补充输入、取消、恢复与委派，以及两种主内核的完整任务对照还没有验证。** 独立固定流程的交付阶段另议。具体输入、版本、失败和限制都从[实验索引](../../research/spikes/README.md)进入。

仓库和文档的基础整理已完成；当前先实现一段主任务代码，交给用户审阅。研究报告和技术字段继续保留，放在需要查证时打开的位置。

## 一次标准开发循环

1. **写清用户要做的事。** 例如“用户创建自主任务时选择 AgentScope 为主内核，运行时能查看任务进度并继续等待子任务”。在[故事表](../product/02-user-stories.md)写出成功、失败和不支持时各会看到什么。
2. **列出已有证据和未知点。** 官方文档说支持什么、本机到底跑过什么分开记录。没有跑过的行为写“未验证”。
3. **做最小实验。** 固定框架版本和合成输入，只验证眼前一个风险。保留首次失败、修正后的代码、结果和运行命令。
4. **比较实现做法。** 看用户体验、需要自写的代码、恢复与升级风险。大方向写入 ADR；`Proposed` 表示仍在讨论，`Accepted` 才是选定路线。[决策索引](../architecture/decisions/README.md)区分当前提案和历史提案。
5. **做一个可演示的功能。** 契约、代码、必要测试和说明放在同一个小改动里。实验脚本不能直接当产品内核。功能完成后按故事逐项验收。
6. **请用户看实际行为。** 展示任务怎样运行、哪里失败、哪些代价还不知道。讨论后的修改进入下一轮，不把整套产品一次做完。

路线、安装依赖、费用和权限范围等重大取舍交给用户评审；常规实现、修复和验证由研发继续完成。

## 接下来的编码增量

每写完一段，就展示代码、实测结果和缺口，等用户看过再定下一段；下面是待评审的顺序，不表示后续代码已获批准。

1. **本轮：正式代码里的文字主任务最短路径。** 产品按用户指定的内核启动根任务；先接入 AgentScope，测试产品模型接口、逐次授权的本地工具、未注册内核的明确拒绝和公开事件投影。[正式代码](../../src/xuanyue/)与[产品测试](../../tests/test_runtime.py)是本段交付；合成运行的[独立实验与结果](../../research/spikes/agentscope-primary/README.md)保留在研究目录。
2. **下一段候选：补充输入、取消和跨进程恢复。** 在同一主任务上分别制造暂停、重启和失败，核对状态与副作用；历史节点分叉单独报告支持或不支持。
3. **再下一段候选：反向 A2A 委派。** AgentScope 主任务调用 LangGraph 子任务，按已有反方向实验的同类输入核对父子身份、等待输入、取消、产物、断线和重复提交。
4. **对照与路线评审。** 让两种内核分别担任主智能体运行同一合成任务，比较功能缺口与适配代码，再决定正式产品接口；独立固定工作流的调度路线另议。

本轮通过只证明第一段列出的机制。两向委派、真实模型、完整轨迹、沙盒和桌面交付均需各自验收；阶段划分仍以[产品目标](../product/01-product-brief.md#分期建议)为准。

## 文档和代码怎么放

| 需要找什么 | 去哪里 |
| --- | --- |
| 产品目标、用户故事 | `docs/product/` |
| 当前内核设计、对象字段和架构决策 | `docs/architecture/`；旧 ADR 从[索引](../architecture/decisions/README.md)辨认 |
| 上游证据、版本与原始结论 | `docs/research/` |
| 自编实验、锁文件、合成输入和公开结果 | `research/spikes/`，每项有 README；第三方源码在被忽略的 `research/upstreams/` |
| 已开始的产品代码与测试 | `src/xuanyue/`、`tests/`；客户端入口以后按评审结果增加，每段只增加当下所需内容 |

README 给第一次来的人看；一篇主题文档只回答一个问题。字段表、协议细节和负测保留在技术参考页，主文章给出具体例子和链接。当前需求、待评审方案、已测事实和历史提案要明确标注。提交前检查相对链接、章节、故事编号与阶段描述。文档本身也按 [US-051](../product/02-user-stories.md#9-仓库与文档) 验收。

## 验证与 Git

工程机制、模型质量、数据正确性、界面、沙盒和三平台安装分别报告。先固定输入和期望结果，保留失败、跳过及未判断；不能为了通过而改答案。合成模型证明执行步骤，真实模型还要单独评估效果、费用和延迟。有副作用的故障注入先用合成接收方，记录实际重试次数和写入次数。

设计文档与自编实验一起提交。新分支默认用 `codex/<topic>`；提交说明写清改变了什么。公开仓库只包含自己的文档、代码、锁文件和合成结果，不放第三方整仓、依赖环境、业务数据、密钥和运行数据库。发布前查文件范围与凭据；推送后核对仓库可见性、远端提交和本地工作树。项目许可证仍待确定。详细约束见[AGENTS.md](../../AGENTS.md)。
