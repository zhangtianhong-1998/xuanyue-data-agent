# 两种 Agent 内核都能担任主智能体

[返回设计入口](../00-discovery-summary.md) · 相关：[核心对象](03-core-contracts.md)

**目标用法：**用户编排工作流时，指定 AgentScope 为主智能体、LangGraph 为子智能体并保存版本。想改由 LangGraph 主持，就编辑并保存另一个版本。运行时必须按对应版本执行。目前只完成 LangGraph 主、AgentScope 子的单向局部实验，反方向和完整任务仍待验证。

修订：2026-09-26；状态：**双主智能体是已确认需求；具体工作流实现路线待验证和评审**。原“LangGraph 固定主编排、AgentScope 只做子执行器”的建议已撤回。[ADR-0004](decisions/ADR-0004-dual-primary-kernel.md)记录这次修订；协议与切换规则集中在[多内核设计](08-runtime-interoperability.md)。

按问题查阅：第 1 节解释主智能体与工作流执行器；第 2 节列出框架实验能证明什么；第 3 节比较仍待选择的工作流路线；第 4 节是两种主内核共同的验收要求；第 5 节说明下一项实验。

## 1. 两种内核都能担任主智能体

这里的**主智能体**是一次用户任务的顶层负责人：接收目标、提出公开计划、选择模型与工具、委派和汇合子任务、请求用户输入、交付结果，并对暂停、恢复、取消和轨迹负责。用户在编排工作流时指定这个角色及其内核，选择随流程版本保存。产品不得自动改选另一内核。

**工作流执行器**负责运行用户在画布上保存的节点、边、路由和检查点，不负责替用户决定谁是主智能体。若采用产品自有的调度层，它只调度预定义节点，不能代替用户指定的主智能体制定计划、委派和整合结果；若采用框架各自的工作流适配器，所选内核也必须按相同的产品规则执行。两条实现路线目前都未获批准。

| 必须覆盖的任务形态 | 用户应看到的结果 | 当前证据 |
| --- | --- | --- |
| 单主任务：LangGraph 或 AgentScope | 任意一种都可作为根运行，完成计划、工具调用和结果交付 | 分别有局部机制实验；尚无同一完整主任务对照 |
| 同内核父子 | 主 Agent 可委派、等待、汇合，并能解释失败 | 尚未按统一契约做双内核对照 |
| LangGraph 主 → AgentScope 子 | 统一任务、状态、产物和轨迹入口 | [现有 A2A 实验](../../research/spikes/runtime-interoperability/README.md)仅验证这一个方向的局部行为 |
| AgentScope 主 → LangGraph 子 | 与反方向相同的产品契约 | 尚未实验，下一门槛之一 |
| 用户修改主智能体并保存新流程版本 | 新版本可预检、执行和恢复；旧版本与历史仍可查看 | 尚未完成双主对照；原生检查点不承诺互转 |

## 2. 现有框架证据支持什么

共同情境及原始结果见[对照研究](../research/09-framework-comparison.md)，不能把通过数量当作产品评分。实验使用合成模型，框架版本和 Python 环境各自锁定。

| 能力 | AgentScope 2.0.8 | LangGraph 1.2.12 | 对双主需求的影响 |
| --- | --- | --- | --- |
| Agent 循环、消息与工具 | 原生 Agent、typed blocks、工具和事件；真实循环实验已运行 | 图节点可封装模型和工具循环，产品需定义规范消息与工具代理 | 两者都有成为主 Agent 的基础；尚未证明完整产品体验相同 |
| 固定流程、路由与并行 | 发布包实验中路由由应用实现；固定 main 的 SOP/Router 与发布包不能混称 | 条件边、并行合流有本地固定图验证 | 同一 WorkflowDefinition 如何运行仍待选型 |
| 暂停、重启与任务状态 | AgentState/HITL 加应用落盘通过局部实验 | SqliteSaver、interrupt/resume 通过局部实验 | 需要以两种主绑定重复相同故障场景 |
| 历史节点分叉 | 已测发布包未实现等价 F05；不能推断不可能 | checkpoint/history/update_state 加应用分支登记通过局部实验 | AS 侧须补机制或验证可用方案，不能用静默禁用代替双主 MVP 要求 |
| 父子 A2A | 已验证作为被委派的一端 | 已验证作为父流程的一端 | 反向和同内核父子尚未验证 |
| 公开轨迹、授权与预算 | 框架事件可作为来源，产品仍需持久化和策略 | 同样需要产品持久事件与策略 | 两边必须按相同的产品契约验收，不能把内部日志称为完整轨迹 |

版本与证据：[AgentScope 发布包及固定源码](../research/06-agentscope-evidence.md)、[LangGraph](../research/07-langgraph-evidence.md)、[A2A](../research/10-a2a-interoperability.md)。手写固定图通过的项目只证明局部机制可实现；如果选择产品自有调度层，还要独立估算并发、恢复、迁移和维护成本。

## 3. 仍需比较的两条工作流路线

| 路线 | 实现方式 | 需要重点证实 |
| --- | --- | --- |
| 产品持有持久工作流调度 | 产品调度已定义的节点与分支，用户指定的 PrimaryAgentRuntime 负责计划、委派和整合 | 调度层会增加多少自建状态机；配置为 AS 主运行时，它是否真正拥有根职责；节点回溯、取消与副作用是否可一致实现 |
| 双 WorkflowRuntime 适配 | LangGraph 与 AgentScope 各自运行从同一 WorkflowDefinition 编译出的流程，产品统一事件和产物 | AS 发布版/自有适配器如何支持 DAG、持久检查点、历史节点分叉；两种引擎的结果与恢复语义如何对齐 |

上表是候选，不表示已经选择“自研内核”或“两个现成框架自动兼容”。A2A 只处理 Agent 间通信；它不提供用户画布编译、跨内核 checkpoint 转换或完整内部节点轨迹。原生状态留在原内核；新任务切换、交接点创建新运行与原任务恢复是三种不同操作，见[多内核设计](08-runtime-interoperability.md)。

## 4. 双主 MVP 的共同验收线

用**结构相同、主智能体配置不同**的两份合成工作流，分别让用户在编排时指定 LangGraph 和 AgentScope，记录实际根调用与版本。两次运行都需通过以下用户可见行为，才能称两种主内核均可用：

1. 主任务独立接收目标、制定公开计划、调用受控工具、委派子任务、汇合结果，并按同一规范消息与产物交付。
2. 同一固定流程可进行确定性步骤、受限模型路由、人工检查；两边的权限、预算、画像读取及失败状态按相同规则执行。
3. 关闭主进程后按声明的检查点恢复；取消、待答输入、子任务失败和结果未知均有一致的产品状态与可见轨迹。
4. 从**产品声明支持的历史节点**创建新尝试、比较并选定结果。节点粒度必须对用户写明；不能把“整个任务重跑”展示成“从节点恢复”。
5. 两个方向的跨内核委派经 A2A 验证；若用户流程要求某项能力，任一主绑定缺失时明确报不兼容，不声称已实现无感切换。

这条共同线不要求两个框架的内部对象或隐含推理一致。模型输出和费用可能不同，比较时固定模型、提示、输入和预算，并报告差异；不能仅凭工程测试判断回答质量。

## 5. 下一次只推进一个验证门槛

本轮先纠正文档与验收线。下一次优先做 **AgentScope 独立主运行** 的小实验：同一合成任务的计划、工具、委派、等待输入、重启恢复与公开事件，明确是否有 LangGraph 进程参与。随后单独做 AgentScope 主 → LangGraph 子的 A2A、以及产品可见历史节点分叉。现有 LG 主 → AS 子结果继续保留为单向证据。

取得这些结果后，再比较两条工作流路线的实现量和缺口，形成供用户评审的选型决定。当前不把任何内核设为唯一默认，也不把尚未通过的 AgentScope 历史分叉说成已有能力。
