**1. P1：AgentScope 会在长会话中删去历史，产品仍保存为正常完成**

事实：给两个内核各传入相同的八轮历史，每条用户文字约 19,021 字符，均低于当前 HTTP 的 20,000 字符单条限制。AgentScope 的实际模型请求中八个历史标记全部消失；LangGraph 保留全部八个。AgentScope 仅向模型附加“早期消息已截断”提示，产品公开事件没有截断或覆盖缺口，SQLite 最终状态仍为 `completed`。结果见[合成观察记录](../../research/spikes/design-alignment-audit/observations.json)的 `long_history`。

原因：[AgentScope 桥](../../src/xuanyue/engines/agentscope.py)第 144–149 行没有指定产品侧上下文容量；第 380–392 行只调整 `max_image_num`，保留了框架默认压缩与失败后截断策略。本机 AgentScope 2.0.8 的模型基类默认 `context_size=32768`，压缩阈值为其 80%。压缩需要结构化输出，而本桥第 168–185 行拒绝相关选项；框架随后退回截断。产品增加图片数量上限，并不能防止整个旧消息随上下文压缩被移除。

设计依据：[消息契约](../architecture/03-core-contracts.md)第 45、74–77 行要求转换和裁剪可识别；[多内核规则](../architecture/08-runtime-interoperability.md)第 48、63 行要求不能删除历史后继续冒充完整执行。[当前会话说明](../engineering/04-local-session-ui.md)第 17、37 行也承诺带入完成轮次，并表示不会悄悄省略历史图片。这里已超出“长会话费用未评估”的范围，实际输入已被改变。

建议：下一切片先关闭压缩失败后的静默截断，并在进入框架前做明确的输入容量检查；超限就停止并解释。容量取自所选模型的登记与验证结果，不能永久硬编码成框架默认值。若以后实现摘要，单独评审摘要规则，保存原消息引用、丢失范围和转换事件。验收同时覆盖超阈值文字历史、混合图片历史和压缩失败；比较两种内核实际交给模型的输入，不能只检查 `Task.history`。

**2. P1：AgentScope 工具异常正文会写入公开记录，并继续传给模型**

事实：登记一个合成只读工具，执行时抛出含 `SYNTHETIC_SECRET_MARKER_DO_NOT_EXPOSE` 的 `RuntimeError`。AgentScope 将该正文写入 `tool_result_delta`，经现有消费函数保存进 SQLite，并交给下一次模型调用。脚本模型继续回复后，Run 为 `completed`。相同异常在 LangGraph 路径中抛到产品层，Run 为 `failed`，公开记录只有安全类别。见观察记录的 `tool_exception`。这是合成标记泄露验证，未发现或使用真实密钥；当前默认乘法工具通常不会产生这类敏感异常。

原因：[AgentScope 工具包装](../../src/xuanyue/engines/agentscope.py)第 270–288 行把 `ToolService.invoke` 的异常直接交给 SDK；AgentScope 2.0.8 的 `Toolkit.call_tool` 将一般异常的 `str(e)` 转成工具返回。之后第 308–312、343–348 行把工具返回正文当公开内容投影。[ChatService](../../src/xuanyue/chat.py)第 232–240 行的安全处理仅对真正抛出框架的异常生效，无法拦住已经转成工具文本的异常。

设计依据：[核心对象](../architecture/03-core-contracts.md)第 41 行要求安全错误，不把 traceback 或凭据送入 UI；[US-024](../product/02-user-stories.md)第 54 行要求密钥不进入 UI/日志；[当前会话说明](../engineering/04-local-session-ui.md)第 19 行限定安全失败类别。

建议：在产品工具边界建立明确的安全错误结果，区分可展示的业务错误与未分类异常；未知异常正文不得进入模型或公开事件。两套适配器使用同一错误策略，分别验收权限拒绝、参数错误、业务失败和运行时异常。工具失败后是否允许 Agent 继续解释，应由产品规则决定；“失败工具之后仍给出回复”本身不等于分析正确或错误，不能一律以有没有最后一段文字判断任务质量。

**3. P2：LangGraph 会把尚未发生的模型调用记成“已开始”**

事实：脚本模型连续要求调用乘法工具，触发当前递归上限。LangGraph 实际模型请求 4 次、工具执行 4 次，但公开轨迹出现 5 条 `model_call_started`，随后因 `GraphRecursionError` 失败。多出的第五条没有真实模型请求。AgentScope 对照为 4 次模型请求、3 次工具执行、4 条开始事件，终态 `incomplete`。见观察记录的 `iteration_limit`。

原因：[LangGraph 适配器](../../src/xuanyue/engines/langgraph.py)第 546–552 行在收到全部工具结果时，预先生成下一次模型开始事件；图可能在真正进入模型前就因递归上限停止。第 391–395 行的首次开始事件也在图运行前生成。前端[调用统计](../../desktop/src/components/RunActivity.tsx)第 52–61 行按这些事件统计模型调用，因此这不是只存在于内部日志的差异。

设计依据：[本段公开调用关联](../engineering/04-local-session-ui.md)第 39–43 行要求显示实际模型与工具调用；[公开轨迹规则](../architecture/04-workflow-and-trace.md)第 98–102 行要求状态对应真实执行，不能伪造。

建议：从模型桥真正开始处理调用的位置产生事件，再与图中的消息及工具关联。图只决定下一步时，可记录“待调度”，不能计作模型调用。新增递归上限、模型前校验失败、调用异常的对照，核对实际请求数与事件数。这里不需要先实现完整计划树或子 Agent 事件。

**4. 扩展前必须补：出站授权与不可变运行绑定**

事实：[模型配置编辑器](../../src/xuanyue/model_config_editor.py)第 228–275 行只禁止删除仍被会话引用的模型 ID，允许原 ID 改目的地或上游模型名。合成配置实验确认，仍被会话引用的 `m` 可以从第一个虚构域名改为第二个；实验没有联网。下一轮由[ChatService](../../src/xuanyue/chat.py)第 183–218 行重新读取现行配置，并带入此前完成的问答及图片。Run 只存 `kernel` 和产品 `model` 字符串，[表结构](../../src/xuanyue/storage.py)第 126–138 行未保存当时的目的地、上游模型、配置版本、框架和适配器版本。

因此旧 Run 的模型身份无法靠当前配置复原；用户修改模型目录后，旧会话的后续请求会带历史发往新地址。前端只在新建会话的选择菜单展示目标域名，正常输入区域未展示当前目的地或本次历史发送范围（[App.tsx](../../desktop/src/App.tsx)第 791–815、842–850 行）。产品当前也没有每次请求使用的授权对象。

这是[工程说明](../engineering/04-local-session-ui.md)第 81 行已披露的模型可变绑定限制，不据此宣称本次发生了未经授权的数据外发。它与[US-025](../product/02-user-stories.md)第 55 行的项目/供应商/范围授权、[运行绑定](../architecture/08-runtime-interoperability.md)第 36、46 行的目标之间仍有明确缺口。

建议分成两个小单元：先给每个 Run 保存不含密钥的模型目的地、上游 ID、配置版本及内核/适配器版本快照；随后让模型调用携带项目和有效授权引用，校验本次文字、历史和附件范围。目的地或范围变化时重新匹配授权，不必对未变化的相同范围反复确认。正式真实数据输入应在这条路径验收后接入。原生安全存储另列平台切片，不能把现有 `0600` 文件称为已完成系统钥匙串托管。

**5. 扩展前必须补：统一限制、失败状态和附加模型调用记账**

事实：当前 `Task` 只有本轮身份、内核、模型和消息，[类型定义](../../src/xuanyue/types.py)第 61–70 行不含预算或截止时间。AgentScope 写死 `max_iters=3`；LangGraph 写死 `recursion_limit=8`，它们不是同一个计量单位。本次循环对照也显示工具次数和终态不同。`timeout=45.0` 设置在供应商客户端，不能当作整项任务的总时长或工具执行上限。会话有单 Run 互斥，但不同会话各启一个后台线程（[ChatService](../../src/xuanyue/chat.py)第 220–226 行），没有产品总并发与共享预算管理。

首轮标题在主 Run 完成后通过另一个模型请求生成，[ChatService](../../src/xuanyue/chat.py)第 262–302 行和[现行说明](../engineering/04-local-session-ui.md)第 31 行明确未将其纳入 Run 轨迹、用量和费用。当前标记 token 用量未知是诚实的，不能由此推导已经有费用控制。

这属于已知的 K1 能力缺口，不应把尚未交付的预算服务当作当前小切片失约。但[双主验收线](../architecture/02-kernel-selection.md)第 54–59 行和[US-031](../product/02-user-stories.md)第 61 行要求同一规则。

建议：先统一单 Run 的最大模型调用数、工具执行次数、整体截止时间和超限原因；框架限制保留为第二道保护。标题以关联到会话的独立调用记录保存状态与用量，未知值仍标未知，并使用同一出站与预算入口。再按独立切片处理用户取消、工具超时和任务恢复，不要把所有生命周期功能合进一次大改动。

**6. 文档与开发顺序需要同步，尚不能据此认定此前切片未经授权**

事实：[产品分期](../product/01-product-brief.md)第 54–57 行把 K0b 用于主任务/反向委派验证，K0c 用于方案评审；[开发时间线](../engineering/progress.html)第 524 行已把 K0c 用于图片输入，第 649 行使用了产品分期中没有解释的 K0f。历史 [ADR-0004](../architecture/decisions/ADR-0004-dual-primary-kernel.md)第 18–22 行仍表述“先双向实验再决定实现阶段”，但[现行研发流程](../engineering/01-development-process.md)已明确允许代码增量与路线评审并行。另有小处过时：[设计导航](../00-discovery-summary.md)术语表仍写“单张用户图片”，与现行四图能力不一致。

判断：仓库缺少一个清楚说明“哪些最小接入已采用、哪些生命周期与调度方案仍待定”的现行决策基线。仅凭仓库不能重建全部用户审批历史，因此不能把这些差异直接定性为擅自开发。

建议：统一阶段与切片编号，或明确 K0c/K0f 只是切片别名；给 ADR 添加现状说明并链接现行研发流程，保留原提案的历史状态，不直接把整个候选架构改为 Accepted。更新导航的图片数量。后续优先级建议是：先处理本文三处当前偏差，再逐段评审授权/绑定、执行限制和生命周期；反向 A2A 保持独立实验门槛。

从产出分布看，当前产品主要提供聊天、模型配置、附件与执行记录，经营数据分析尚未进入产品。这个事实与 README 的范围声明一致，不能据此判定偏离用户授权。但如果继续只扩展聊天界面，业务目标会一直没有产品证据。建议在基础控制切片明确后，选择一次最小 CSV 任务，贯通“确认两期口径 → 确定性计算 → 保存数据/查询/结果来源 → 显示有引用的结论”；两种主内核使用同一数据工具。已有[数据契约实验](../../research/spikes/data-analysis-contract/README.md)可作证据起点，不能直接搬实验代码充当产品验收。D1 不必等待全套画布、画像和本体服务，也不应把自然语言答复当作可核对的计算结果。
