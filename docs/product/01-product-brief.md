# 产品需求草案 v0.1

日期：2026-09-24。状态：愿景已记录；首版用户与数据边界已确认；功能范围和技术路线待评审。

## 1. 已确认的方向

做一个在 macOS、Windows、Linux 运行的 Data Agent 客户端。先在当前 Mac 开发，以个人可用版本为目标。第一类用户是需要分析经营数据的业务人员，核心任务是导入文件、发现异常、下钻分析和形成报告。

用户于本轮确认：

- 首版优先经营数据分析，而非通用办公或代码工作台。
- 数据保存在本机；向云模型发送必要内容须经用户授权。
- 用户主导需求，Codex 协助研发；暂不按完整企业平台投入。

产品要逐步具备多 Agent、MCP、Skill、Memory、模型能力适配、可配置 TTS、可编排分析流程和深度研究。后续本体与语义层通过 MCP 接入，本项目只预留接口，不实现该服务。

## 2. 首个完整使用场景

业务负责人导入最近两期的订单明细，问：“本月销售额为什么下降？”

1. 检查工作表、日期范围、货币、金额列、退款、缺失、重复以及数据粒度；需要时请用户确认口径。
2. 展示公开的分析计划：比较总量、按维度定位变化、检查候选解释、生成报告。用户能改筛选和取消任务。
3. 在本机查询，展示销售额变化以及地区、渠道、商品等维度的贡献。检查是否存在样本变化或数据质量问题。
4. 用户点击地区或渠道，页面保留完整筛选条件和对比期，支持返回上层及查看贡献明细。
5. Agent 提出有数据支持的候选解释，标出反例、证据不足和仍需补充的数据。
6. 报告中的数字可以回到查询、文件版本、口径和图表。导出到用户指定目录。
7. 用户确认的指标口径和偏好可保存，下一次分析同一项目时使用；数据变化后旧结论不能自动变成当前事实。

这一场景是用于讨论的示例，行业、具体指标、样本文件和最大数据规模仍待用户确定。

## 3. 产品界面建议

参考现代 Agent 客户端的任务与产物交互方式，自行设计数据分析工作台。

| 区域 | 用户看到什么 | 主要操作 |
| --- | --- | --- |
| 左侧项目与任务 | 项目、数据集、历史分析、保存的流程 | 建项目、切换任务、恢复分析 |
| 中间对话与任务过程 | 问题、公开计划、执行状态、需要确认的口径 | 提问、补充信息、改计划、停止 |
| 右侧分析工作区 | 数据预览、图表、报告、来源、流程 | 筛选、下钻、返回、查看明细、编辑报告 |
| 设置 | 模型、云端传输授权、MCP、Skills、Memory、TTS | 测试连接、查看权限、撤销授权 |

默认展示业务结论和交互控件；SQL、工具调用和运行记录按需展开。不要把 Python 环境、模型 token 和工具 JSON 放进普通业务用户的主要操作流程。

## 4. 分期范围建议

以下是建议优先级，不是已确认的交付承诺。

| 阶段 | 可验收结果 | 暂不纳入 |
| --- | --- | --- |
| M0 需求与技术验证（当前） | 需求、故事、候选架构、源码证据、关键实验、待决策项 | 完整产品开发 |
| M1 最小完整原型 | 一份 CSV → 口径确认 → 本地查询 → 可下钻图表 → 带来源报告；任务可取消；云调用有授权 | 任意 Python/终端工具、自动联网研究 |
| M2 个人 MVP | CSV/XLSX/Parquet；受控多 Agent；本地 MCP；受审查 Skill；项目 Memory；流程模板、恢复；三系统安装验证 | 企业多租户、插件市场 |
| M3 增强分析 | 可视流程编辑、远程 MCP、视觉材料分析、TTS、多步骤研究、增强诊断 | 自动因果定论、无人值守业务执行 |
| M4 后续扩展 | 语义层 MCP、团队治理、更多连接器，分别立项 | 本轮不建设本体服务 |

多模态/TTS 可以在 M2 提前做小型适配验证，但不应推迟数据分析核心验收。若用户要求它们随首版发布，需要相应缩减其他功能。

## 5. 分析质量要求

- 数值计算交给可复现的查询或分析函数；LLM 负责理解问题、提出计划和解释结果。
- 不清楚“收入”的定义、时区、退款处理或比较基期时，先澄清，不能猜成已确认口径。
- 下钻必须带着相同数据版本、指标定义、时间比较与父级筛选。仅切换图表外观不算下钻。
- 加法指标可做贡献拆解；比率、去重人数、库存等指标需要专用聚合规则。
- “变化主要集中在华东渠道 A”是描述；“因为某活动导致销售下降”是因果判断，需要额外证据。
- 多个 Agent 的一致意见不等于独立证据。所有结论都要引用可追溯的观察或计算结果。
- 研究检索要保留来源、日期、引用范围和冲突；外部网页内容不能获得本地工具执行权限。

## 6. 非功能需求与待验证目标

| 维度 | 首版要求 / 建议门槛 | 如何验收 |
| --- | --- | --- |
| 平台 | macOS、Windows、Linux 均为产品目标 | 各系统独立安装、导入、运行、取消、恢复、导出；Mac 通过不能替代其他系统 |
| 数据 | 原始文件不可静默覆盖；每次导入有内容哈希和解析版本 | 文件更新能生成新版本并使旧缓存失效 |
| 安全 | 只访问用户选择的项目数据；模型调用经过统一出口 | 拒绝未授权文件、未授权云端内容、日志中的密钥 |
| 可恢复性 | 暂停、关闭窗口、worker 退出都有明确状态 | 重启后不会重复发布产物或自动重复外部副作用 |
| 可观察性 | 用户看得见公开计划、工具状态、成本和异常 | 能定位失败步骤；不收集隐藏推理 |
| 性能 | 先用 10 万 / 100 万行合成数据分档评测，再确定正式上限 | 记录机型、RAM、大小、列类型、冷启动和峰值内存；本轮小样本不作性能证明 |
| 安装体验 | 最终用户无需手动安装 Python/Node | 干净系统测试；签名和系统提示单独记录 |
| 可维护性 | 文档、契约、业务逻辑、适配器分层 | 替换模型或桌面外壳时不改指标算法 |

## 7. 本轮尚未确认

1. 首批行业与数据样例：电商、门店销售、SaaS 经营等；金额、数量和转化率哪类最重要？
2. 实际文件规模、工作表数量、是否常有多表关联，以及 Mac 的可用内存约束。
3. 首选模型服务与大致单任务预算；“发送必要内容”的默认授权范围。
4. 初版是否接受先支持固定分析流程，再开放拖拽编排。
5. MVP 是否必须包含多模态和语音，还是先交付可扩展接口与后续版本。

先讨论第 1、4、5 项即可进入方案评审；模型供应商可在连接测试前确定，不要求现在提供密钥。
