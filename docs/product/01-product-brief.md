# 产品需求与阶段范围

[返回设计入口](../00-discovery-summary.md) · [用户故事](02-user-stories.md)

日期：2026-09-25；状态：用户方向已确认，具体范围和技术路线待评审。

## 已确认的目标

做一个 macOS、Windows、Linux 上运行的 Data Agent 客户端，先在当前 Mac 开发个人版本。首个业务场景仍是经营数据分析：导入文件、发现异常、下钻、形成有来源的报告。数据默认保存在本地，必要内容经授权发送给云模型。

根据本次反馈，**研发顺序改为先确定并验证 Agent 内核，再接入完整 Data 功能**。内核需要多 Agent、可编辑混合工作流、长期用户画像、统一多模态消息、全轨迹与历史分叉、MCP/Skills 和执行沙盒。新增需求要求多内核可注册、可替换，并允许父子 Agent 使用不同内核，通过 A2A 扩大互通范围。后续本体/语义层服务只留接口，不在本项目实现。

## 内核 MVP 的完整使用场景

用户建立任务，选择或编辑一个流程：固定工具处理输入 → 小模型选择路径 → 两个 Agent 分别完成子任务 → 用户检查 → 保存产物。过程中可以查看所有公开步骤、停止、关闭后恢复。对不满意的结果，从历史节点改参数或模型重新运行，比较两个尝试，选定一个；旧记录仍可查看。系统使用可查看和纠正的项目偏好，生成代码经沙盒执行。父任务可由 LangGraph 编排，子任务由 AgentScope 执行；普通界面保持一致，能力不足、出网变化和恢复限制仍如实提示。

先用合成工具和材料验证这条路径，避免把指标算法、BI 组件和内核缺陷混在一起。随后将工具替换为数据导入、查询、图表和分析方法，保持同一套运行与权限协议。

## 分期建议

| 阶段 | 交付与验收 | 此时不承诺 |
| --- | --- | --- |
| K0 选型与方案评审（当前） | 三路线与 A2A 证据、机制/混合内核实验、核心协议、故事和阅读路径 | 完整产品已经实现 |
| K1a 可运行内核 | 一个真实模型服务；受限多 Agent、混合节点、持久恢复、规范消息/事件、本地 MCP/Skill、预算与授权；LG 默认编排、LG/AS 子执行器及 A2A 委派；合成流程可跑 | 面向普通用户的完整客户端 |

| X 按需扩展 | 第二种完整流程编排器、更多 A2A 服务/版本、远程 MCP、TTS、深度研究、语义层对接、更多连接器 | 本轮开发本体服务或企业多租户 |

K1 指 K1a 与 K1b 的合并范围，可分多次小交付；不能因为 K1a 命令行可跑就宣布内核 MVP 完成。K1 在开发 Mac 验证并建立跨平台测试入口；只有三端安装/运行实测通过，才称跨平台版本。多模态消息协议在 K1 固定，实际识别能力按适配器逐项验收。

## 非功能要求

所有阶段都要求：凭据不进轨迹；权限不随模型输出扩大；取消、失败、未知和部分完成有明确状态；历史输入与产物可定位；费用未知时标未知；代码、流程和依赖版本可记录与复现。最终用户不应为运行客户端自行配置 Python/Node，但沙盒后端是否需要额外安装是待评审取舍。

数据规模、性能与模型质量不能从小样本实验推断。D1 再固定业务样例、指标答案与规模档位；K1 先固定执行语义、路由标签集和故障注入场景。多内核与无感切换的范围见[多内核设计](../architecture/08-runtime-interoperability.md)。具体规则见[研发流程](../engineering/01-development-process.md)。

## 这次需要讨论的范围

本轮先确定：是否接受 LangGraph 默认编排器和多内核子执行器的分工；是否接受 K1a/K1b 的内核优先节奏；个人预览版是否可依赖本地容器/虚拟机沙盒。首个行业和 BI 组件细节放到 D1 评审，不再提前阻挡内核选型。
