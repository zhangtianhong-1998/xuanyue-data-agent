# 我们要做的产品

[返回阅读入口](../00-discovery-summary.md) · [全部用户故事与验收](02-user-stories.md)

状态：需求与技术路线仍在讨论，产品代码开始逐段实现。下面把**用户已经提出的目标**和**尚未选定的技术做法**分开写。当前还没有可用的客户端。

## 从一次任务看产品

用户把经营数据文件放进本地项目，问：“这个月收入为什么下降？”客户端先检查文件和指标口径，再计算变化。用户可以点图表继续下钻，查看每个结论用到的数据，最后修改并保存报告。数据留在本机；需要云模型处理内容时，客户端先核对用户授予的数据范围和目的地。

这是先做的文件分析场景。用户还希望直连数据库，或通过现有 API/MCP 数据服务按需取数；这些来源不必先整体导入本地。口径归属和取数方式见[Data 协议](../architecture/07-data-contracts.md)，接入阶段待讨论。

用户也可以直接把目标交给自主 Agent。Agent 可阅读 Skill，再根据当前情况选择分析方法、工具或子 Agent。任务运行时能看到公开步骤、工具结果、失败和分支；下次打开客户端能接着处理。生成代码只能进入受限执行环境。

用户创建自主任务时，选择主智能体及其 **LangGraph 或 AgentScope 内核**。两种内核都要能接收目标、制定计划、委派子任务并整理结果。另有规则更固定的工作流：用户保存步骤、条件和输入输出，编排时也指定主 Agent 及其内核。主 Agent 可以按流程把某一步派发给子 Agent；步骤固定不等于没有主 Agent。Agent 自主运行一段时间后调用已保存的确定性工作流，是后期研究方向。[三种用法](../architecture/04-workflow-and-trace.md#先看懂这页)

两个方向的跨内核委派都要支持：LangGraph 主→AgentScope 子，以及 AgentScope 主→LangGraph 子。用户看到的任务、消息、产物和流程入口保持一致；能力差异要如实显示。工作流的底层调度方式仍在比较中，见[内核设计](../architecture/01-candidate-architecture.md)。

## 项目目标

1. **个人可用的跨平台客户端。** 先在当前 Mac 开发，再分别验证 macOS、Windows 和 Linux 的安装、运行和导出。只在 Mac 通过时称 Mac 预览版。
2. **可替换的 Agent 内核。** LangGraph、AgentScope 都能运行主智能体：自主任务由用户创建时选定，工作流由用户编排时选定；子 Agent 的内核也可另行指定。以后增加内核时，通过产品接口接入消息、工具、状态和产物；界面不依赖某个框架的内部对象。
3. **可核对的数据分析。** 数据来源、口径、计算、图表和报告能互相追溯。异常、贡献和可能的解释分开呈现；证据不足时说明缺什么。
4. **可追溯的自主任务与可编辑的固定流程。** 用户能查看公开运行轨迹，从声明支持的历史节点派生新会话，或在当前会话把后续切到新分支并保留旧路径供切回；也能保存并编辑确定性流程。长期偏好可查看、修改和删除。
5. **人能读懂的仓库。** 新读者从 README 能看出项目做什么、做到哪一步、下一步是什么；在两次跳转内找到当前方案、用户故事或实验。每项实验有目的、运行方法、结果、失败与未验证范围。一个概念只有一处现行详细说明，其他页面给链接。第三方源码、依赖环境、业务数据和密钥不进入项目提交。

MCP、Skill、沙盒和多模态消息属于内核接口设计；TTS、深度研究与后续语义层 MCP 按阶段接入。当前不开发本体服务。[用户故事](02-user-stories.md)列出逐项验收；本页只说明整体目标。

## 业务分析能力：哪些先做，哪些后做

下表判断能力是否值得做，并给出可先验证的切片；它不改变现有阶段安排，也不批准新功能排期。这些能力可以共用数据访问、证据和执行轨迹。详细验收只放在[用户故事](02-user-stories.md)，计算和证据规则只放在[分析方法](../architecture/09-data-analysis-methods.md)与[Data 协议](../architecture/07-data-contracts.md)。

| 能力 | 当前判断 | 可先验证什么 | 后续再扩展什么 |
| --- | --- | --- | --- |
| 智能问数 | 值得做，面向用户 | 在已选文件上问一个范围明确的问题；含糊时澄清，答案附口径、查询和来源 | 接入更多来源后，再验证跨源问数 |
| 智能取数 | 值得做，支撑问数与分析 | 先完成已选文件的基础取数；多源接入后才验证按问题选来源 | 数据库、API/MCP 的能力判断、取数范围和执行位置，不默认全量拉到本地 |
| 数据异常分析 | 已在 D1/D2 草案中，继续做 | 先按确认的两期窗口和阈值找变化，显示触发规则并支持下钻 | 评估时间序列异常和误报/漏报；不把异常直接称为根因 |
| 归因分析 | 值得单列；已有部分验收草案 | 先拆解哪些分组的增减构成总量变化，核对抵消与剩余项 | 再结合价格、销量、结构等数据检验候选解释；因果效应研究另行评审 |
| 数据洞察 | 值得做，先有证据再筛选 | 先汇集变化、异常和贡献拆解；每条发现可回到图表和查询 | 再从多项发现中筛选、排序、合并重复项，检查反例；不把相关性写成因果 |
| 分析思路 | 值得做交互原型，形态待讨论 | 比较分析前的问题拆解、运行中可调整的计划、可复用方法三种用法 | 用户选定用途后再确定对象和保存方式；不直接等同固定工作流或 Skill |
| 深度研究 | 值得保留，放在后期 | 用获准的内部资料或外部材料开展多轮查证，形成有来源的报告 | 冲突证据、来源失效和长任务恢复单独验收 |

“智能问数”是用户怎样提问和得到答案；“智能取数”是为这次问题选来源、检查权限并取得可信结果。异常分析先确认发生了什么；归因先核对哪些部分构成了变化，再检验可能的解释，不能把贡献直接称为原因；洞察再判断哪些发现值得看。深度研究是较长的多轮查证任务，可只用内部资料，也可在授权后加入外部材料。现有 K1 的 Agent 执行计划只显示它将做什么；“分析思路”要给用户哪些编辑权，仍需原型验证。

作为范围对照，[Microsoft Fabric Data Agent](https://learn.microsoft.com/en-us/fabric/data-science/how-to-create-data-agent)将结构化问数与复杂根因问题分开；[Power BI 分解树](https://learn.microsoft.com/en-us/power-bi/visuals/power-bi-visualization-decomposition-tree)按维度下钻并推荐高低值，本项目将这种结果视为排查线索，而非因果证明；[Tableau Pulse](https://help.tableau.com/current/online/en-us/pulse_insights_platform_insight_types.htm)分别列出异常、趋势与贡献等洞察类型；[Gemini Deep Research 帮助](https://support.google.com/gemini/answer/15719111?hl=en)说明研究计划与多来源报告。官方资料于 2026-09-26 查阅，只用于比较能力边界，不证明本产品已实现这些功能。

## 分期建议

每一步先展示结果和缺口，再确定下一步。阶段代号用于追踪工作，不代表用户必须一次批准所有实现。

| 阶段 | 这一步只解决什么 |
| --- | --- |
| 已完成基础整理（K0a） | 整理仓库、重写阅读入口，明确双主内核和适配边界。 |
| 当前逐段验证（K0b） | 用合成任务分段验证 AgentScope 独立主运行，再验证它通过 A2A 委派 LangGraph。现有反方向实验作为对照，失败也保留。 |
| 方案评审（K0c） | 根据双向证据比较自主 Agent 的实现与恢复；固定流程的调度路线另行评审。 |
| 内核可运行（K1a） | 两种主内核分别跑通同一自主任务、恢复、委派、权限、预算和产物保存，不要求先画工作流。 |
| 工作台（K1b） | 创建自主任务时选择主内核，查看和比较公开历史尝试；分批接入真实模型、MCP、Skill、画像和沙盒。 |
| 独立确定性工作流（阶段待讨论） | 编排、保存并单独运行固定步骤与模型路由；是否纳入 K1 尚未确定。 |
| 数据分析（D1、D2） | 先完成 CSV、口径确认、计算、图表下钻和来源报告；再扩展文件格式、多表与复杂诊断。 |
| 扩展数据来源（阶段待讨论） | 比较数据库原位查询与本地计算，接入已有 API/MCP 数据服务，再验证多源智能取数；明确远端结果保存策略和受管理口径的归属。 |
| 以后（X） | 研究自主 Agent 调用已保存的确定性工作流；评审可编辑分析思路与深度研究；更多 A2A 服务、远程 MCP、TTS 和语义层对接。 |

只有两种主内核都通过同一组必需行为，才称“双主内核 MVP”。小型合成实验只说明测试过的机制；模型质量、真实费用、沙盒隔离和三平台发行需要各自验收。当前[已知结果与下一步](../engineering/01-development-process.md)会随每一道门槛更新。
